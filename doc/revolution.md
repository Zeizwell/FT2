# ZX Evolution Revolution (ZX Revo) — концепт пользователя и разбор

Концепт написан пользователем (2026-10-12), здесь — краткое содержание и выводы разбора.
Связано: `doc/evo-rev-d.md` (что уже есть в rev D+), `doc/zx-trinity.md` (карта Тринити).

## Суть концепта

microATX-компьютер: **настоящий Z80 + 2 × настоящих AY + большая ПЛИС** как чипсет.
- Режимы-«профили» одной прошивки ПЛИС: **Pentagon 128K(++)** — база legacy, **TS-Conf+** — развитие
  TS-Config, **Native** — своё.
- Единая RAM (~16 МБ) за общей memory fabric (шина 32 бит и шире), все мастера через неё:
  Z80, native CPU, видео, GPU, DMA звука / сети / SD / FDC, устройства шины.
- Общий DMA (RAM ↔ всё), видео из нескольких трактов + компоновщик, текстовый режим 90×36 с оверлеем,
  native 2D-ускоритель (copy / fill / blit / line / scale / rotate…), потом 2.5D и простое 3D.
  Raster events вместо Copper.
- **REV-BUS** — новая шина расширения «как PCI по смыслу»: MMIO, окна, DMA, bus mastering, IRQ,
  обнаружение устройств; ×4 слота. ZXBUS — 1–2 слота для legacy.
- MPU / DMA firewall, профили ≠ контейнеры ≠ bitstream, гость (legacy) и хост (Revo OS), сброс
  зависшего гостя без перезагрузки машины.
- Native CPU и Revo OS — не выбраны. Wi-Fi вместо Ethernet. ВГ93 — внутри ПЛИС.
- 6 слоёв, зоны: быстрая цифра (ПЛИС + RAM), 5 В (Z80 + AY), аналог, RF, видео, шины.

## Зачем (со слов пользователя)

Главное — не 3D (это внешняя карта), а **расширяемость**. В Еву толком ничего не подключить:
порты медленные, DMA с периферией не работает, нормального маппинга памяти для устройств нет, арбитра
DMA нет. Тринити упирается ровно в это (обмен через окно 0, `/WAIT`, поток через порт).
Значит, суть Revolution — **fabric + общий DMA с арбитром + REV-BUS с MMIO и bus mastering**,
а не видео и не GPU.

## Что хорошо

- Чёткое разделение: **bitstream** (железо) / **профиль** (какая машина) / **контейнер** (что
  запускаем). Профили без перепрошивки ПЛИС — правильно.
- Pentagon 128K как одна legacy-база вместо зоопарка машин; TS-Config как основа расширенного режима —
  весь софт под TS (и FT2) работает сразу.
- Не резервировать VRAM навсегда — совпадает с моделью TS (видео в любой странице).
- Raster events как команды видео вместо отдельного Copper — дёшево и полезно.
- Зоны на плате и упор на землю / return path, а не на расстояния — грамотно.

## Риски и нестыковки

1. **Объём.** Это компьютер + своя ОС + GPU + свой стандарт шины + виртуализация. Годы работы команды.
   Главный вывод прошлых разговоров: железо живёт, только если под него пишут софт. Native-режим без
   софта мёртв; legacy-режимы — живут сразу.
2. **Native CPU нельзя выбирать последним** (п.14 плана). От него зависят MMIO, карта адресов, шина
   fabric, REV-BUS, ОС. Естественный вариант — софт-ядро RISC-V внутри ПЛИС (VexRiscv и т.п.): без
   лишней микросхемы, прямо на fabric. Внешний SoC — свой мост и своя шина.
3. **Настоящий Z80 и состояние гостя.** Регистры живого Z80 снаружи не прочитать: «save current state»
   (п.49, 53) — только через NMI и программный сброс регистров в память (как Multiface / NMI в TS).
   Заложить NMI-обработчик в схему переключения.
4. **Boost.** Z84C0020 — максимум 20 МГц. «Быстрее 14» с настоящим Z80 упирается в чип.
5. **Z80 на общей памяти.** Z80 нужна детерминированная задержка (тайминг Пентагона, без тормозов).
   Арбитр обязан гарантировать слот Z80 в каждом его цикле, видео и GPU — в остальное время. С SDRAM
   решаемо, с DDR (большая латентность, refresh) — сложнее, нужен буфер / кэш со стороны Z80.
6. **REV-BUS ×4 слота без единого устройства.** Свой стандарт шины + параллельная шина по 4 слотам на
   скорости = сложность и сигнальная целостность. Делать, когда появится первое реальное устройство;
   начать с 1 слота. Первый кандидат на устройство — Тринити.
7. **Корпус ПЛИС.** 16 МБ DDR / SDRAM, HDMI, Z80, 2 × AY, ZXBUS, REV-BUS — это 250+ ног: почти
   наверняка BGA. Пайка — только заводом (PCBA) или ПЛИС на готовом модуле + своя плата-носитель.
8. **5 В.** Z80, AY, ZXBUS — 5 В, ПЛИС — 3.3 В: буферы на всю шину (десяток корпусов, учесть задержки
   на 14 МГц).
9. **2.5D / 3D** — реальны только на средней ПЛИС (Cyclone V / Artix-7 класса), не на мелкой Gowin.
   Правильно, что в конце плана.
10. **Текстовый режим 90×36 (п.18) — только коды символов.** FT2 нужен **атрибут** (paper/ink) на
    каждое знакоместо, X-офсет и 256-байтовые строки как в TS. В профиле TS-Conf+ — как есть в TS;
    в native-режиме — не терять атрибуты.

## Что делать, если делать

Лестница, где **каждая ступень полезна сама** (софт есть сразу):

1. **Ева на новой ПЛИС:** настоящий Z80 + AY + TS-Config 1:1 (+ Pentagon как профиль). Уже полезно:
   весь софт TS работает, место в ПЛИС с запасом.
2. **TS-Conf+ малыми добавками:** порт позиции растра, DMA порт ↔ память, raster events, больше RAM.
   Их сразу использует FT2 / демо (то, что обсуждали для форка TS-Config).
3. **REV-BUS + fabric с арбитром** — это суть проекта, поэтому рано: 1 слот, первое устройство —
   Тринити (окно памяти на шине, DMA в обе стороны, bus mastering вместо окна 0 и `/WAIT`).
4. **Native CPU** (софт-ядро) + простая ОС / загрузчик.
5. **2D-ускоритель** native. 3D — внешняя карта на REV-BUS, не в основной ПЛИС.

ПЛИС: для ступеней 1–2 хватает корпусов с ногами (EP3C25 PQFP-240, Gowin GW2A-18 LQFP-144,
Cyclone IV/10 EQFP-144 — до ~25К ячеек, 80–150 ног). Полный набор (16 МБ, HDMI, Z80, 2 × AY,
ZXBUS, REV-BUS) — 250+ ног, это BGA (модуль или заводская пайка).

Z80: настоящий тянет 5 В-буферы, потолок 20 МГц, состояние только через NMI. Ядро Z80 в ПЛИС
снимает всё это и позволяет несколько гостей сразу. Вариант: ядра по умолчанию, настоящий Z80 —
опциональным разъёмом; AY — настоящие.

Свою ревизию «той же Евы» не делаем (`doc/evo-rev-d.md`: rev D+ уже закрывает VDAC, USB, звук).
Revolution имеет смысл только как ступень 1+ (новая ПЛИС), а не как перекладка платы.

## Решения (обсуждение 2026-10-12)

### Первая версия — только база архитектуры

Без AY, без совместимости. Ядро Z80 (один мастер) + **fabric + арбитр + контроллер SDRAM** + общий DMA
+ REV-BUS (мастер + MMIO) + простейшее видео из общей памяти (нагружает арбитр, показывает результат).
TS-Config, Pentagon, AY — потом, профилями поверх готовой базы. Сначала документ архитектуры, потом
симуляция (Verilator / Icarus — гоняю сам на ПК), потом железо.

### Память — SDR SDRAM, не DDR3

- DDR3: BGA-память + BGA-ПЛИС с банками SSTL, fly-by, 1.5 В + VTT, капризное IP-ядро, большая и
  плавающая задержка (плохо для Z80). Полоса в гигабайты нам некуда.
- Надо < 100 МБ/с: Z80 14 МГц ≈ 14 МБ/с худший случай, видео 360×288×8 бит×50 ≈ 5 МБ/с
  (640×480@60 ≈ 18), DMA / REV-BUS — десятки.
- SDRAM 16 бит: 200 МБ/с (100 МГц) / 266 МБ/с (133 МГц) пачкой, ~60–80 нс случайный доступ.
  TSOP-54, паяется руками, простой открытый контроллер (так MiST / MiSTer / порт TS-Config).
  32 бита (2 чипа) — вдвое. Против Евы (DRAM, порядка 14 МБ/с на всех, моя оценка) — в 10–20 раз.
- SRAM — идеальный тайминг для Z80, но мало и дорого; разве что быстрым буфером.
- Архитектура (fabric + арбитр) от типа памяти не зависит — меняется только контроллер.

В EP1K50 быструю память не поставить: ПЛИС полна, а TS-Config построен вокруг слотов старой DRAM.
«Реворк Евы под быструю память» = новая ПЛИС + SDRAM.

### ПЛИС и стенд

- У всех производителей старшие модели — только BGA. Не бояться: держать вендорные примитивы (PLL,
  блочная память, SDRAM-контроллер) в отдельных обёртках — переход на старшую модель меняет обёртки
  и распиновку, не логику. ПЛИС — на модуле, тогда меняется модуль, а не плата.
- **Gowin** (китайские, дешёвые, ретро-сцена: Tang Nano 20K / Primer 25K / Mega 60K, 138K): одна
  среда Gowin EDA от младших до старших, есть открытый тулчейн; документация хуже, порта TS-Config
  нет — переносить (умеренно).
- **Cyclone**: знакомый Quartus, есть порт TS-Config на MiST (Cyclone III + SDRAM). Пользователю
  не нравится (старшие — BGA, «опять переделывать») — довод выше снимает это для любого вендора.
- Стенд: Tang Nano 20K (GW2A-18, SDRAM в корпусе, HDMI, microSD, встроенный программатор, ~25–30 $)
  или QMTech Cyclone IV EP4CE15 + SDRAM 32 МБ (~25–35 $ + USB-Blaster ~5–10 $). Устройство на
  REV-BUS для проверки — Raspberry Pi Pico 2 (заодно прототип Тринити).

### Профили: TS-Config 1:1 + свой режим с нуля

- **TS-Config — профиль без изменений** (переносим 1:1, сверяем с живой Евой). Его видео и DMA —
  клиенты общей fabric.
- Расширять сам TS можно только так:
  1. добавлять в свободные номера регистров (`#xxAF`);
  2. всё новое — **за ключом** (как «TRIN» у Тринити): без ключа машина = TS-Config 1:1;
  3. **скорости меняются только под ключом** — иначе ломаются демки, завязанные на тайминг DMA /
     памяти.
  Малые добавки (порт растра, DMA ↔ порт, окно устройства, быстрый DMA) — сюда, под ключ.
- **Native-режим с нуля** — для большого: 2D-движок, кадровые буферы, новая адресация.
  Не «всё с нуля», а **идеи TS, развитые дальше**: строка с шагом степени двойки (256 / 512, шире —
  1024 / 2048: старший байт = строка, `inc h`), экран = страница в общей карте (двойной буфер даром),
  аппаратные офсеты. Снимаются лимиты TS: фиксированные режимы до 360×288, 85 спрайтов / 2 слоя,
  окна 16К на большой буфер, 8-битные счётчики DMA. Текстовый слой — с атрибутами (как FT2).
  Процессор — то же ядро Z80, быстрее (28–56 МГц). Первый софт native — FT2.

### Развёртка: машинная отдельно от вывода

- Внутри — **виртуальная развёртка гостя** (Пентагон: 71680 T, 320 строк, INT, бордюр). Картинка
  строится строка за строкой в такт виртуальному лучу → мультиколор, бордюр, растровые трюки работают.
- Строки пишутся в буфер; **вывод (HDMI / VGA) — в своём режиме** (576p50 / 720p50) с масштабом.
  Для старых режимов вывод **50 Гц** — кадр в кадр, без рывков скролла.
- Native — своя виртуальная развёртка (640×480, 720p…).
- На выходе **компоновщик слоёв**: гость в окне + native-слой (ОС, отладчик, второй гость).
- INT 50 Гц для музыки — свой таймер, не зависит от видео.

### DMA — дескрипторы в памяти, один процессор команд

- CPU пишет **один указатель** на дескриптор; у дескриптора поле «следующий» → цепочки на весь кадр,
  готовятся заранее, переиспользуются.
- Дескриптор фиксированного размера (16 / 32 байта, выровнен): источник и приёмник (полные
  физические адреса), ширина × высота + шаг строки у обоих (2D сразу), операция (copy / fill / blit
  с прозрачностью / … 2D), флаги (**ждать строку N** = raster events, IRQ по концу, продолжить),
  следующий (или 0).
- **DMA + raster events + 2D-движок = один процессор команд**, не три блока.
- Регистр статуса («где сейчас цепочка») и стоп — для отладки и сброса зависшего гостя.
- MPU проверяет адреса самих передач (иначе гость затрёт хост).
- Мелочь (4 байта) пишет CPU сам — отдельный путь не нужен.
- Первая версия: только copy + fill + цепочка + IRQ. Потом «ждать строку», потом 2D по одной операции.

### Арбитр

- **Гарантированные слоты:** Z80 — в каждом своём цикле (тайминг не плывёт); видео — подкачка строки
  заранее, со сроком.
- Остальное время — DMA-каналы и REV-BUS, пачками.
- Приоритеты каналов: реального времени (звук, raster events) выше массовых (копирование, блиттер).
- 4 банка SDRAM: пока один открывает строку, другой отдаёт данные — арбитр это учитывает.
- Самая критичная часть — гонять в симуляторе под полной нагрузкой (Z80 + видео + DMA + шина) до железа.

### Не пихать всё в ПЛИС — периферию на отдельные микросхемы

Правило: **в ПЛИС — то, что живёт в такт памяти и развёртки; протокольное и медленное — снаружи.**
- **МК** (CH32V307/317 как в rev D+, или RP2350): USB-хост (HID, флешки, хаб), часы, питание, кнопки,
  загрузка / обновление прошивки ПЛИС, Wi-Fi (ESP32-модуль). К ПЛИС — по SPI как **внутреннее
  устройство REV-BUS** (окно, DMA, IRQ): шина проверяется на нём с первого дня.
- **Видео:** параллельный RGB 24 бит + синхро (~28 ног) → на одной шине **ADV7125** (VGA) и
  **HDMI-передатчик** (ADV7513 / IT66121, умеет звук по HDMI через I2S). Оба выхода сразу, ПЛИС не
  нужны TMDS-ноги — подходит любая.
- **Звук (не в первой плате):** I2S-ЦАП (PCM5102 и т.п.), 3 ноги. AY и аналоговый тракт — отдельно, как в rev D+.
- **SD** — с ПЛИС (SPI / 4 бит, 4–6 ног), чтобы DMA лил сектора в память.
- В ПЛИС остаётся: Z80 / ядро и шины 5 В, SDRAM + fabric + арбитр + DMA, генерация видео, REV-BUS,
  ZXBUS, SPI к МК, SD, I2S. Меньше ног — может хватить корпуса с ногами.

### Первая плата — скелет и разъёмы, звука нет совсем

Никакого звука на первой плате: ни AY, ни ЦАП / PCM, ни бипера, ни усилителя. Только ПЛИС, SDRAM,
Z80 (или ядро), МК (USB), видео, SD, разъёмы ZXBUS / REV-BUS. Звук — потом, отдельно (как сводятся
AY, бипер, ковокс, Тринити, HDMI-звук).
Хочешь звук — карта в ZXBUS (TurboSound, NeoGS, Тринити) со своим выходом. Для этого порты AY
(`#FFFD` / `#BFFD`) и прочие незанятые ПЛИС порты должны выходить на ZXBUS.

Оценка (2026-10, LCSC / Ali, грубо): прототип компактный 4 слоя, паять самому ~150–300 $ (5 плат +
детали поштучно); microATX 6 слоёв + заводской монтаж ~400–700 $; вторая итерация — закладывать.
В серии (50+) себестоимость ~60–100 $ — уровень готовой Евы (140 $ с монтажом и наценкой).

### Идея: REV-BUS = несколько каналов QSPI с DMA (обсуждение 2026-10-12, не решено)

Повод: VDAC4 / Tang Nano 20K VDAC — всё на одном SPI Евы (общая шина, два CS, MISO через мультиплексор, ≤ 28 МГц).
- **2–4 независимых канала QSPI**, у каждого свой DMA и IRQ: устройство на своём канале, без общих CS и выбора MISO.
- QSPI (4 линии данных) на 50–100 МГц — ~25–50 МБ/с на канал; каналы работают параллельно. Около 7 ног на канал.
- Устройства — дешёвые готовые модули, которые QSPI умеют сами: ESP32-S3, RP2350, Tang / Gowin.
- **Bus mastering через пакеты:** устройство шлёт «запиши / прочитай по адресу», мост в ПЛИС исполняет через fabric
  (с проверкой MPU). Для устройства это как свой доступ к памяти, без широкой параллельной шины и сигнальной
  целостности на слотах.
- Обнаружение: команда «кто ты» (ID, версия, возможности) на каждом канале.
- На Еве так не сделать: ноги IDE уже заняты (видео VDAC2 + SPI), EP1K50 полна.

### Своя плата сразу (как делали Еву)

Можно без стенда, но до разводки обязательно:
1. Решения, влияющие на плату: настоящий Z80 / ядро / разъём под опцию; память 16 или 32 бит; ноги и
   число слотов REV-BUS; видео (RGB-шина на ADV7125 + HDMI-передатчик); USB через МК; AY — разъём или
   распаять.
2. **Пустой проект распиновки**: все ноги, PLL, заглушки SDRAM и видео — собрать в среде вендора
   (клоки на клоковые входы, SDRAM в одном банке, напряжения банков, тайминги SDRAM сходятся). 1–2 дня.
3. Разводка по проверенной распиновке.
4. Пока плата едет — fabric, арбитр, DMA в симуляторе.

### Процессор и частоты

- **Точный тайминг нужен только на 3.5 МГц** (Пентагон, старые демки): арбитр даёт Z80 гарантированный
  слот, ожиданий нет. Под точные 7 МГц софта нет — там всегда были такты ожидания и везде по-разному.
- **7 / 14 / 20 МГц — кэш + `/WAIT` на промахах**, как на Еве сейчас на 14 (и лучше: SDRAM отвечает
  быстрее старой DRAM).
- SDRAM: полоса огромная, но Z80 нужна **задержка** одного доступа: промах строки ~60–80 нс,
  попадание в открытую строку ~20–30 нс (код идёт подряд — в основном попадания).
- **Настоящий Z84C0020 на 20 МГц** — штатно (это паспорт). Клок с ПЛИС — через буфер 74AHCT/HCT
  (3.3 В мало), переключение частоты — без огрызков, по фронту (статический CMOS, можно хоть
  останавливать). Выше 20 — лотерея по экземплярам, не закладываться.
- **T80 в ПЛИС** (оценка, точно покажет синтез): логика ~50–70 МГц на Gowin GW2A, ~60–90 Cyclone IV,
  100+ Cyclone V / Artix-7. Потолок — память: 28 МГц без проблем (как Next), 56 — с кэшем в блочной
  памяти. 100+ — только конвейерное ядро, не повторяющее такты (для native допустимо).
- **eZ80 микросхемой** (3.3 В, LQFP, 24 бит = 16 МБ плоско, в 2–3 раза быстрее Z80 на такт, Agon Light):
  цена не страшная (eZ80F92 ~9–17 $, eZ80F91 ~17 $, 2026-10), но **доступность плохая** — сроки
  32–47 недель, склады пустые, часть вариантов снята. Основой не брать. Открытого ядра eZ80 нормального
  нет; своё совместимое ядро в ПЛИС — возможно потом (система команд документирована), месяцы работы.
  Native CPU — в ПЛИС.

### Revo OS

- **Вид — окна в стиле Спектрума** (решение пользователя): шрифт 8×8, цвета атрибутов, бордюр, яркие блоки;
  красиво, как хорошая ZX-программа / демо-меню. **Не** текстовый Нортон, как в NedoOS («где тут Спектрум»),
  и не как мир TS-Config — Wild Commander в текстовом режиме, как DOS. Если брать SymbOS — только так:
  **графические окна**, а не текст режим. Текстовый слой — для приложений (FT2), не для оболочки.
- SymbOS — красиво, но приложения «тощие»: всё рисует CPU (окно потащил — перерисовка), приложение рисует
  через сообщения ОС, 64 КБ адреса на приложение, многозадачность — переключением. На Revo это снимает
  железо: **окно = аппаратный слой компоновщика** (приложение рисует в свой буфер, перетаскивание — смена
  координат), рамки / заливки / шрифт — 2D-движок, текстовый слой с атрибутами, MMU и 32 МБ.
- Тяжёлое (трекер, редактор, демки, игры) — **на весь экран** напрямую; окна — утилиты и ОС поверх.
- Основа: свой оконный слой поверх порта готовой ОС (NedoOS — ZX-шная, работает на Еве; SymbOS; Fuzix) —
  что брать, не решено.
- Что ОС должна под Revo: страницы на всю память + MPU по задачам; перебор REV-BUS и драйверы по ID, общий
  диспетчер IRQ; DMA как сервис (проверка адресов дескрипторов, очередь); гости (контейнер в своём участке,
  окно в компоновщике, снимок через NMI, сторож); события ввода от МК; FAT32 + образы TRD / SCL / FDI;
  сеть — TCP/IP в ESP32, ОС даёт сокеты; обновление прошивок; монитор, UART, **эмулятор native на PC**.
- Порядок: загрузчик + монитор (отладка железа) -> ОС -> гости и окна.

### 2D-движок (что даёт быстрая память + место в ПЛИС)

fill / copy, blit с прозрачностью и маской (любое число спрайтов), scale / rotate (аппаратный
ротозум), line, смешивание (8 бит — через таблицу). Полный экран 360×288×8 (~100 КБ): на Еве DMA —
почти весь кадр, на SDRAM — ~1 мс (~5 % кадра); 3–4 полноэкранных операции за кадр — с запасом.

Схема признана правильной: по сути Амига (Copper + Blitter) / DMA в PC / командные буферы видеокарт,
объединённые в один процессор команд.
